【Title】OmniKVQuant: KV Cache Quantization for Omni-LLMs  
arXiv:2609.11582 · 2026-09-10

- 一句话总结：把旋转量化从纯文本 KV 扩到音视频 Omni-LLM，2-bit + fused Triton decode，不建 FP16 中间 cache。
- 核心贡献（2-3点）：
  - 诊断 TurboQuant 在多模态 cache 上的两个失败模式：temporal key drift、跨模态 value 几何不一致。
  - 训练无关：短窗重标定 key range + 按模态独立 rotate value。
  - Qwen2.5/3-Omni 上 2-bit，7 个 AV bench 基本保住精度，并给 fused 解包 kernel。
- 工程价值：直接可插 decode 路径；Omni 服务里 KV 随音频/视频帧线性涨，这是少有“能落地的多模态 KV 量化”。kernel 比算法更值得抄。
- 是否值得读：强烈推荐（做多模态 serving / KV 量化）
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.11582

【Title】Building py-kvcache: External KV Caching for vLLM with NVMe  
arXiv:2609.11744 · 2026-09-10

- 一句话总结：vLLM 外置 KV（GPU/CPU/NVMe）的实测手册：什么时候该 load cache，什么时候重算更快。
- 核心贡献（2-3点）：
  - 瓶颈不在带宽，而在 transfer 粒度、staging 内存、以及 I/O 何时进入 scheduler。
  - connector：async DIO + 有界 staging + 排队期预取；80k token 从盘加载比 LMCache 快 2.0×（预取 1.34×）。
  - H100 + 短前缀时外置 cache 可能亏；弱卡/长前缀才划算。结论是 admission policy，不是“永远 offload”。
- 工程价值：生产级 KV offload 的决策树。有代码，对照 LMCache / 原生 KV Offload。
- 是否值得读：强烈推荐（做 serving / prefix cache）
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.11744

【Title】Phase-Decoupled, Model-Calibrated Power Control for Disaggregated LLM Serving  
arXiv:2609.11133 · 2026-09-10

- 一句话总结：PD 分离后 prefill/decode 功耗特性相反，厂商 Max-Q 一套参数两边套会亏；按模型校准分 lane 控功率。
- 核心贡献（2-3点）：
  - Prefill：SM-clock 窗口，下限由延迟 SLO 保证；Decode：在吞吐/延迟悬崖上方自动标定 power cap。
  - 8×B200、Qwen3-Coder-480B FP8：+20.4% tokens/J，e2e +3.5%，优于 Max-Q 的 +8.6% / +5.2%。
  - 声明主要对 MoE 成立；dense 收益约 1/5。三日稳态省 32.3% 电。
- 工程价值：功率已是 serving 容量上限。这是少见的“PD + 功耗 + SLO”同框论文，可直接改运维策略。
- 是否值得读：强烈推荐（集群运维 / PD 架构）
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.11133

【Title】Composable CXL Memory as a Kubernetes-Native Shared Memory for LLM Serving  
arXiv:2609.10790 · 2026-09-09

- 一句话总结：把可组合 CXL 做成 K8s DRA 资源，vLLM 跨节点共享同一物理 KV 区，不需要外部 metadata。
- 核心贡献（2-3点）：
  - DRA driver：按需拼 CXL → DAX → 同一 CDI 名注入多节点 pod。
  - slot directory 嵌在共享介质里，省 metadata 服务。
  - 两节点 512GiB CXL + Qwen2.5-7B：跨节点 prefix 命中时 TTFT 降 5.5–36.6×，跨节点 vs 同节点只差 1–4%。作者自称 feasibility，不是大规模 perf paper。
- 工程价值：共享 KV 的“操作系统层”路径，比再写一个 cache 服务更接近集群现实。规模小，别当吞吐结论。
- 是否值得读：可选
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.10790

【Title】KVShareArena: KV-Cache Reuse Across Contexts and Model Checkpoints  
arXiv:2609.10266 · 2026-09-09

- 一句话总结：Prefix cache 在 RAG/多 agent 里经常错位、错 checkpoint；给跨 context / 跨权重复用做统一评测与成本账。
- 核心贡献（2-3点）：
  - 指标：相对“全重算 vs 无 cache”缺口的回收比例；单独记建 cache 一次性成本。
  - 单源：改 position 就够；多源拼接必须部分重编码或训练，否则比不用 cache 更差。
  - 换 checkpoint：无训练修复几乎不受影响；在一个 checkpoint 上训的 adapter 会掉。有 pip + leaderboard。
- 工程价值：agent/RAG serving 的 cache 语义终于有可比实验。别再默认“prefix hit = 免费”。
- 是否值得读：强烈推荐（agent / RAG infra）
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.10266

【Title】T1: Terminal Agent Reinforcement Learning for Long-Horizon Tasks  
arXiv:2609.11042 · 2026-09-10

- 一句话总结：122B MoE 在真实 shell 里 RL，300+ tool-call；用 TITO + MoE routing replay 把训推 logprob 对齐，Terminal-Bench 2.1 43.8% → 64.0%。
- 核心贡献（2-3点）：
  - 系统配方：critic warm-start、按 verifier 数的稠密过程奖励、turn 边界 drift repair。
  - R3：记录 rollout 每层 expert 选择，训练时 replay，训推 Δlogp 0.021→0.013，loss 区零 token drift。
  - 训练数据与 Terminal-Bench 隔离；LHTB 27.9%，超过 GPT-5.4 / GLM-5.1（同 harness）。
- 工程价值：Agent RL 的可复现系统件（slime + SGLang + routing replay）比分数本身更有用。长程 MoE agent 训练的稳定性问题写得很具体。
- 是否值得读：强烈推荐（agent RL / 训推一致性）
- Relevance Score：5

## 今日最值得读 Top 3

1. **py-kvcache** — 立刻能改调度器：外置 KV 是 admission 问题，H100 上盲目盘缓存会亏。有对照实现。  
2. **Phase-Decoupled Power Control** — PD 已是标配，功耗是容量；分 lane 校准比套 Max-Q 更接近生产。  
3. **T1** — 长程 terminal agent 的完整 RL 系统配方 + MoE routing replay，同时覆盖 Agent 与 Alignment/RL。

并列关注：**OmniKVQuant**（有 kernel）、**KVShareArena**（RAG/agent cache 语义）。

## 今日趋势观察

- **Inference / KV 系统仍是主航道**：量化（含 Omni）、外置层级、跨节点共享、非前缀复用同一周扎堆。  
- **Serving 从“吞吐”扩到“电与控制面”**：功率 cap、Ray 控制面 O(N²)、流式 proxy 成为一等瓶颈。  
- **Agent 论文开始写系统细节**：sandbox、verifier 奖励、训推一致性，而不只是 prompt scaffold。  
- SFT/经典 RLHF 新方法偏少；增量在 **agentic RL + 训推对齐**。

## 值得跟进的潜在方向

1. **非前缀 KV 复用协议**：RAG 多 chunk / agent 报告的 position 修复 + 部分重编码，需要进入引擎而不是论文原型。  
2. **PD 分相位功耗与调度联合**：decode 平坦功耗使 cap 可持续，dense vs MoE 要分开标定。  
3. **MoE agent RL 的 routing replay**：长程 tool-call 下训推不一致会直接毁掉 credit assignment。  
4. **外置 KV 的 break-even 作为运行时策略**：按 GPU 代际、前缀长度、队列等待动态选择 load vs recompute。
