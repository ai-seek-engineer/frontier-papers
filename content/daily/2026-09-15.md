### 【Title】ForgeMegakernel: A General Framework for Efficient Auto-Regressive Model Decode Megakernels
- 一句话总结：用 coding agent + 可验证中间态 oracle，按模型自动锻造 decode megakernel，而不是手写融合核。
- 核心贡献（2-3点）：
  - 十级 milestone 知识库：细粒度 SM instruction stream、用 dependency counter 替代全局 sync、shared-memory buffer pool 做跨 SM 负载均衡。
  - 独立 mid-state test oracle：生成过程中查性能 / 误差 / 精度，避免“生成了但 silently wrong”。
  - 14 个 decode op、8 个模型族（0.6B–13B）：MBU 50.5–85.9%；相对 SGLang 0.5.18 几何均值 **1.21×**，相对现有 megakernel compiler **1.54×**。
- 工程价值：直接打 decode 带宽墙。可嵌 SGLang；GSM8K ragged prompt 下 14 个核都快于原引擎且答案精度相当。对 serving 团队：这是“自动写融合核”路线，比再手搓一层 kernel 更可扩展。
- 是否值得读：强烈推荐
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.12379

### 【Title】Dissecting GPU Utilization for LLM Inference on Nvidia Hopper
- 一句话总结：H100 上“SM utilization 很高”经常是假饱和；decode 的小 batch GEMM 填不满 GMMA 64-row fragment。
- 核心贡献（2-3点）：
  - 把单一 utilization 拆成 8 个 Nsight Compute 可复核视角：fragment fill、occupancy、stall、wave quantization、kernel 选择。
  - vLLM + FA3 + cuBLASLt，扫 cold/warm prefill 与 decode、seqlen、batch。
  - 把利用率缺口钉到具体机制，而不是再报一个 80% SM busy。
- 工程价值：排障手册。小 batch decode 的“算力打不满”是 **tile/fragment 形状问题**，不是再加 batch 就能解。做 kernel 选路、padding、投机长度时必须看 fragment fill，而不是看 Nsight 那个百分比。
- 是否值得读：强烈推荐
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.12923

### 【Title】Rethinking Heterogeneous System Disaggregation for Subquadratic Attention (SQD)
- 一句话总结：PD / Attn-FFN 拆分是给 dense attention 设计的；子二次注意力要把 decode 按 **注意力形态** 再拆。
- 核心贡献（2-3点）：
  - Sparse：top-k selection（扫全量 KV）vs top-k attn+FFN（静态 footprint）。
  - Linear / sliding-window：dense 层 vs 子二次层+FFN。
  - 8×B200 异构代理：GLM 5.2 / Nemotron 3 Ultra / Gemma 4 31B 上 tokens/J 相对最强 GPU-only **+31% ~ +56%**；Rubin+LPX 分析模型吞吐最高 **3.6×**。
- 工程价值：中期 serving 架构，不是今天就能 drop-in。但 DeepSeek/GLM 路线已经在用稀疏/线性注意力，继续按 dense PD 拆会把 top-k 索引和静态算子绑在同一类机器上。对下一代机柜互连与芯片配比有指导。
- 是否值得读：强烈推荐（做 serving / 硬件规划）
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.13134

### 【Title】Building py-kvcache: External KV Caching for vLLM with NVMe SSDs
- 一句话总结：外部 KV（含 NVMe）不是“带宽够就快”；粒度、staging、调度切入点决定盈亏平衡。
- 核心贡献（2-3点）：
  - 异步 direct I/O + 有界共享 staging + scheduler-aware preload（排队时就开始读盘）。
  - 80k token 从盘加载比 LMCache **2.0×**，preload 贡献 1.34×；GPU+CPU+disk 比 LMCache **1.23×**，距 vLLM 原生 offload ~4%。
  - H100 + 生产 trace：很多请求低于 break-even，GPU 本地前缀缓存就够，外置缓存变成负担。
- 工程价值：立刻能用的结论——**外置 KV 是 admission 问题，不是默认打开的功能**。弱卡/长前缀才值；H100 短前缀可能负优化。有实现。
- 是否值得读：强烈推荐（跑 vLLM / LMCache 的人）
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.11744

### 【Title】RoofLang: Enabling AI-Driven Architecting of LLM Inference Systems
- 一句话总结：不在现有软件栈里搜参数，而是用可验证 DSL 让 agent 搜索 serving **架构本身**。
- 核心贡献（2-3点）：
  - workload 表示 + 可验证 mutation 空间 + 实现无关 evaluator。
  - 指出 DeepSeek V4 系列峰值 decode 吞吐可比其他代表模型高 **3.5–39.5×**，主因是紧凑 KV 设计抬 batch、降流量。
  - optimizer agent 在 B300 上给 DeepSeek V4 Pro 找出吞吐+交互性同时提升 **6.23–50.1%** 的新结构。
- 工程价值：偏研究框架，不是生产调度器。价值在于把“搜 kernel 配置”升级成“搜并行/KV/拆分拓扑”。对内部 infra 探索有用，落地成本高。
- 是否值得读：可选
- Relevance Score：3
- Link：https://arxiv.org/abs/2609.12551

### 【Title】UNISON: Near-Memory Scheduler of Session KV Residency for LLM Agents
- 一句话总结：Agent 循环里 tool wait 不是“冷会话”；KV 驻留要用会话级 hazard + 空闲 DMA 窗口调度。
- 核心贡献（2-3点）：
  - SPEAR：用 gap 均值和 turn-indexed hazard 决定谁被踢出。
  - TIDE：把观察到的 tool wait 当 DMA budget，决定谁留在快层。
  - 1415 sessions / 33596 turns：hit rate +0.3~23.1%，AMAT -22~51%，长程 TTFT -58~89%。
- 工程价值：现有 LRU/timeout 会把“等工具返回”当成可丢前缀。Agent serving 的 KV 策略必须跟 loop 事件对齐，否则多轮工具调用会反复 prefill。硬件味重（near-memory），思想可迁到 CPU/CXL 分层。
- 是否值得读：可选（做 agent serving 强烈建议扫结论）
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.09643

### 【Title】Behavior Quotient Learning for Low-Rank Adaptation of LLM Agents (BQ-LoRA)
- 一句话总结：多技能 agent 不必多 LoRA；在“决策分布商空间”里去重梯度，再压进固定 rank。
- 核心贡献（2-3点）：
  - BQB：轨迹更新按决策分布局部密度重加权，避免等价行为反复刷同一方向。
  - DPC：投影到固有 rank 切空间，同时控权重误差和决策分布畸变。
  - AppWorld / BrowseComp-Plus vs 标准 LoRA 及其他低秩方法；有消融。
- 工程价值：减 adapter 存储和路由开销。训练侧方法，不加速 decode kernel，但能简化多技能部署（单 adapter、无 router）。
- 是否值得读：可选
- Relevance Score：3
- Link：https://arxiv.org/abs/2609.12896

### 【Title】OmniKVQuant: KV Cache Quantization for Omni-LLMs
- 一句话总结：文本 KV 量化直接套到音视频会踩 **时间 key drift** 和 **模态 value 几何不一致**；窗口定 range + 分模态旋转可做到 2-bit。
- 核心贡献（2-3点）：
  - 诊断 TurboQuant 在 multimodal cache 上的两类失败。
  - 短窗设 key 量化范围；value 按模态分别 rotate。
  - Qwen2.5/3-Omni，七个音视 benchmark 保性能；Triton decode kernel 边 unpack 边算，不建 dense FP16 cache。
- 工程价值：Omni 模型 KV 涨得比文本快。有 fused kernel 线索，比“再训一个量化器”更接近可上线。
- 是否值得读：可选（做多模态 serving）
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.11582

## 今日最值得读 Top 3

1. **ForgeMegakernel** — 唯一同时有核级加速数字、多模型族、且嵌进 SGLang 的工作。decode megakernel 自动化是接下来 6–12 个月 serving 差异化点。
2. **Hopper utilization 解剖** — 几乎零算法噱头，但能立刻改你看 profile 的方式。很多“再加 speculative / 再加 batch”的决策建立在错误利用率叙事上。
3. **py-kvcache** — 把外部 KV 从“功能开关”改成“按 GPU/前缀长度做 admission”。有代码、有和 LMCache/vLLM 的对照，避免在 H100 上白烧 PCIe/NVMe。

## 今日趋势观察

- **Inference / KV / 拆分** 明显占主导：megakernel、Hopper fragment、NVMe KV、子二次注意力拆分、CXL/PIM（近几日还有 PATTON、CXL shared KV）同一周扎堆。
- **Agent** 从“多 agent 提示词”转向 **会话级 KV 驻留** 和 **单 LoRA 多行为**，系统味变重。
- **SFT / RLHF** 近 48h 工程硬文偏少；RL 新稿多为理论/垂直控制，未进清单。

## 值得跟进的潜在方向

1. **按注意力形态拆 decode，而不是按 prefill/decode 或 Attn/FFN。** 稀疏 top-k 的“索引全 KV”和“算 top-k+FFN”算术强度差一个数量级，现有 PD 分离会错配机器。
2. **外部 KV 的 break-even 作为一等公民指标。** GPU 越快、前缀越短，盘/远端 KV 越容易负优化；需要调度器内建预测，而不是全局开 cache。
3. **Agent wait ≠ idle evict。** tool 等待窗口应被当成 DMA/prefetch budget，否则多轮 agent 的 TTFT 会被自己的 KV 策略打穿。
