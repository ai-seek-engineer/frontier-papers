### 【Title】Building py-kvcache: A Performance Characterization of External KV Caching for vLLM with NVMe SSDs
- 一句话总结：把 vLLM 的外部 KV（GPU/CPU/NVMe）做成可调度的异步 offload，磁盘加载比 LMCache 快约 2×。
- 核心贡献（2-3点）：
  - 测清了「重算 vs 外存加载」的拐点：带宽不是唯一变量，粒度、staging、进入调度的时机更关键。
  - 异步 Direct I/O + 有界 staging + scheduler-aware preload，排队时就开始读盘。
  - 80k token 从盘加载相对 LMCache 2.0×，preload 贡献 1.34×；三层全开相对 LMCache 1.23×，接近原生 KV Offload。
- 工程价值：可直接接 vLLM 生产路径；多轮/不规则 prefix 比纯算法压缩更落地。
- 是否值得读：强烈推荐
- Relevance Score：5
- Link：https://arxiv.org/abs/2609.11744

### 【Title】OmniKVQuant: KV Cache Quantization for Omni-LLMs
- 一句话总结：把 2-bit KV 量化从纯文本扩到音视频 Omni 模型，并给出 decode 侧 fused Triton kernel。
- 核心贡献（2-3点）：
  - 诊断 TurboQuant 在多模态 cache 上的失败：temporal key drift、跨模态 value 几何不一致。
  - 窗口内定 key 量化范围 + 按模态分别 rotate value；训练免费。
  - 2-bit 下保住多数音视 benchmark；decode 时 unpack，不物化 FP16 cache。
- 工程价值：Omni serving 的 KV 内存会先爆；kernel 比「再发一篇 4-bit 文本 KV」更有用。
- 是否值得读：强烈推荐
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.11582

### 【Title】PATTON: Enabling Commodity PIM for Production LLM Serving
- 一句话总结：不改 PIM 计算单元，把 vLLM 式 KV block 生命周期接到商品 PIM 上。
- 核心贡献（2-3点）：
  - 点出 GEMV 布局、单 token write、容量三者冲突。
  - Hierarchical granule + Commit Zone：先高效写，再 commit 到 GEMV 友好布局。
  - 相对基线约 1.95× 速度、4.83× 能效；cache hit 接近原生 vLLM。
- 工程价值：PIM 论文终于开始谈 allocator/mapping/command，而不是只谈 attention kernel。落地仍绑特定硬件。
- 是否值得读：可选
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.11392

### 【Title】ExaServe: Large-Scale LLM Serving on Exascale HPC Systems
- 一句话总结：把 YAML 声明变成 Aurora 上可复现的大规模 vLLM 部署，并测出控制面天花板。
- 核心贡献（2-3点）：
  - 覆盖 scheduler/MPI/加速器选择/本地权重暂存等超算落地细节。
  - 1→256 节点（3072 replica）：非流式近线性，27.1k req/s、3.8M tok/s。
  - 流式被中心 proxy 卡在 ~4.7k req/s；Ray Serve 控制面 O(N²)，256 节点 bring-up ~30 min。
- 工程价值：吞吐数字本身一般，瓶颈诊断对多租户/超算 serving 更有用。
- 是否值得读：可选
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.10812

### 【Title】Ecdysis: Efficient and Effective Training of Runtime Harnesses for LLM Agents
- 一句话总结：harness 进化从「逐条任务试错」改成跨实例失败聚合，训练更快、harness 更稳。
- 核心贡献（2-3点）：
  - 拆开 model-specific 适配 vs harness 系统性缺陷。
  - batch 级跨任务失败模式 + 多角色诊断再改 spec。
  - 相对现有 harness evolution：训练最高 1.84×，推理准确率 +18.56%。
- 工程价值：生产 agent 增益多半在 harness，不在再叠一个 planner。可复用到内部评测循环。
- 是否值得读：强烈推荐
- Relevance Score：4
- Link：https://arxiv.org/abs/2609.11677

## 1. 今日最值得读 Top 3

1. **Miles v0.1** — 把 frontier RL 的工程合同写清楚了：精度、权重同步、true-on-policy、异步 step time。做 post-training 平台的人应先对这份，再看算法论文。
2. **py-kvcache** — 少见的「vLLM + 真实磁盘层级」测量。prefix cache 团队这周优先读，能避免盲目上外存。
3. **Online Draft Co-Training** — 把 speculative decoding 从 serving 技巧变成 RL 训练加速器，并给出 256K CP/PP 的可实现修补。

## 2. 今日趋势观察

- **Inference / KV 仍是最大宗**：量化、驱逐、外存、PIM、跨请求 reuse 同时出现；文本 4-bit KV 已内卷，增量转到 **Omni/推理长 CoT、外存层级、PIM 运行时**。
- **Agent 论文从「多 agent 对话」转向 harness / skill retrieval / 终端 RL**，更接近生产。
- **RL 与 serving 耦合变紧**：draft 共训、异步拆池、routing 版本对齐——训练栈开始按推理引擎约束设计。

## 3. 值得跟进的潜在方向

1. **KV 作为跨请求、跨 checkpoint 的一等公民**（RAG 乱序 chunk、agent 互读报告）：前缀缓存语义已经不够，位置修复 vs 局部重编码的成本模型会变成产品决策。
2. **RL rollout 的推测解码 + 超长 CP**：谁先把「draft 共训」做成稳定默认，谁先砍长程 RL 账单。
3. **Harness 当可训练工件**：失败模式聚合比再训一个 70B planner 便宜，且和评测循环天然闭环。
4. **Serving 控制面**：模型 replica 线性扩，proxy / Ray 控制面先塌；流式网关会成为下一轮系统题。
